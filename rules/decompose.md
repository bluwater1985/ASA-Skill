# decompose — 文档 → 需求 / 任务 拆解保真流程（ASA 增量方法）

> **加载规则**：本文件是 ASA 的"把一份设计 / 修复 / 规格文档拆解成需求 + 任务、且不丢精髓"的强制入口方法。
> 平时【不加载】；**当用户给出一份文档并要求拆解为需求/任务（或帮你补「拆需求、拆任务、把这篇规约落地」）时，必须先读取本文件并严格执行**（严禁凭记忆跳步简写）。
> 一旦触发，本文件全部约束在本会话内成为活跃约束；会话结束自动失效。
>
> 关系：本方法**串起** to-spec（管需求 AC 落盘）与 to-tickets（管任务切片落盘），并补上二者之间缺失的"断言抽取 + 覆盖对账"环节。

---

## 为什么必须有这一步

之前的拆解事故：给一份含大量可验证断言（采样矢高≤0.24、双侧误差叠加<0.5、双弧 10.2→10、BBox 绝不少算 1 单位、TDD 用例）的文档，直接拆出 REQ + 4 个 TASK 后，**REQ 的 acceptanceCriteria 是空的、TASK 的 inputs/outputs 全空，数值界与测试用例全丢了**。

根因：AI 没先把文档的"可验证断言"显式摘出来，就动手建节点 → 精髓在抽取阶段就已丢失，后面任何字段校验都发现不了"缺失物不在字段里"。

**所以本方法的铁律：先抽取断言清单，再落盘，最后对账。** 只要断言的枚举是完整的，覆盖对账就能把"漏掉 0.24 那条"抓出来。

---

## 流程（四步，顺序不可换）

### Step 1：断言清单（Claim Inventory）——重中之重，不可跳过
读完整份源文档，把其中**每一条"可验证断言 / 不变量 / 测试用例 / 排除项"**逐条编号摘出，格式：

```
C1 [数值界/不变量] 采样矢高 ≤ 0.24（来源：文档 §二 修复点1）
C2 [不变量] 离散化循环内禁止 round()（来源：§二.3）
C3 [验收 oracle] 双弧理论净距 10.2 → 最终 round 输出 == 10（来源：§四 测试A）
C4 [验收 oracle] BBox 对 30°~120° R=10000 → max_y == 10000 且四维绝不少算 1（来源：§四.2）
C5 [排除项] parallel_length / min_radius 不做改动（来源：§三）
C6 [语义闭环] is_negative 负极性 → difference() 差集剪裁（来源：§一）
…
```

断言类型至少区分四类：**数值界 / 不可协商不变量、验收 oracle（测试用例）、排除项(out-of-scope)、语义闭环**。
**完整性自检**：通读源文档每一节/每一处 ```` 代码、每个 `≤`/`=`/「必须/绝不」，确认没有漏摘。

### Step 2：按 to-spec 落盘需求（含 AC）
1. 在 `.asa/specs/<源>.md` 末尾追加 `## Acceptance Criteria`，**把 Step 1 的每条断言逐字写成一个 bullet**（`- <断言>`），并标注 `(C#)`。
2. `node .asa/index.js add-req "<标题>" --spec .asa/specs/<源>.md --by <操作人>`（命令自动把 AC 逐字解析为节点 `acceptanceCriteria`，编译器把正文写入 `spec`）。
3. **严禁**先建空 REQ 再手工回填——那正是 AC 变空的根源。

### Step 3：按 to-tickets 落盘任务（含 inputs/outputs）
1. 按**可验证产出**切垂直切片（不是按"改哪个文件"切），每个任务覆盖一组相关的 C# 断言。
2. `node .asa/index.js add-task "<动词开头标题>" --desc <ticket.md> --inputs <a,b> --outputs <c,d> --req <REQ-id> --by <操作人>`，**一次写全**（严禁回填）。
3. `description` 里**声明本任务覆盖的断言编号**（如 `覆盖: C1,C2`），`outputs` 里写可交付物 / oracle。
4. 绑依赖边 `edge add` + `plan-tasks` 编排。

### Step 4：覆盖对账 + 用户确认（关键闸门）
产出一张**覆盖矩阵**，交给用户核对（不是"你看行不行"，而是并排列出断言↔承接处）：

| 断言(C#) | 承接的 AC(REQ) | 承接的 TASK / outputs |
|---|---|---|
| C1 矢高≤0.24 | AC1 | TASK-204 / 采样输出 |
| C2 禁 round() | AC2 | TASK-204 / 采样输出 |
| C3 双弧10.2→10 | AC3 | TASK-204 / tests |
| C4 BBox 极值 | AC4 | TASK-206 / tests |
| C5 排除项 | — | TASK-∞ / "故意不碰"标注 |
| C6 负极性差集 | AC6 | TASK-207 / 面积 |

**对账规则**：任何一条断言若**既没进 AC、也没进某个 TASK 的 outputs/描述**，必须二选一——要么补进去，要么**显式标注 out-of-scope 并给理由**（禁止静默消失）。
**用户确认**：把覆盖矩阵展示给用户并请求批准；未批准不得推进实现。

## 自我审计清单（落盘后、跑 validate 前）

- [ ] Step 1 断言清单是否完整（重读源文档核对，无漏摘）
- [ ] REQ `acceptanceCriteria` 非空，且与断言清单逐条对应
- [ ] 每个 TASK 有 `inputs` / `outputs`，`description` 引用其覆盖的 C#
- [ ] 覆盖矩阵：无"既无 AC 又无 TASK"的悬空断言
- [ ] 排除项显式标注（out-of-scope + 理由），非静默丢弃
- [ ] `node .asa/index.js validate` 无 `SPEC_WITHOUT_AC` / `TASK_NO_IO` 告警

> 引擎已内置两条**非阻塞**告警 `SPEC_WITHOUT_AC`（REQ 有 spec 无 AC）、`TASK_NO_IO`（任务无 inputs/outputs），跑 `validate` 即可自动点名本流程第一步就应满足的底线；本文件补充的是"内容级"的断言覆盖对账（告警查不了，靠 Step 4 与人对账兜住）。
